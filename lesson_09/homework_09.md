## 1. Чтение решений

Заполните до запуска гонки. Время оценивайте через n (длина списка) и k.

| Решение | Время | Верно? |
|---|---|---|
| A | O(n·k): вложенный цикл по следующим k проходам | да |
| B | **O(n·k): на каждом шаге создаётся срез длины k и выполняется линейный поиск `in` по нему** | **да** |
| C | **O(n): один проход по списку с обращением к словарю `last` за O(1)** | **да** |
| D | **O(n): один проход по списку с поддержанием множества `window` размера до k за O(1)** | **да** |
| E | **O(n): один проход по списку со словарём первых вхождений `first`** | **нет** |
| F | **O(n): один проход по списку со множеством `window` неверного размера (k + 1)** | **нет** |

В решении B нет вложенного `for`. Где в нём спрятан второй цикл: **В строке `if nums[i] in nums[i + 1:i + k + 1]:` — Python сначала копирует до `k` элементов при создании среза, а затем оператор `in` последовательно перебирает этот список в поиске совпадения (оба действия работают за O(k)).**

## 2. Две ошибки

Контрпримеры записаны в `counterexamples_09.py`. Здесь объясните по коду,
что идёт не так и какую строку исправить.

Первое ошибочное решение **E**: **В строке `if x not in first:` кандидат записывает только индекс самого первого появления пропуска и никогда его не обновляет. Если первые два одинаковых пропуска стояли дальше чем в `k` шагах, а третий прошёл сразу следом за вторым (например, `[1, 2, 1, 1], k = 1`), программа всё равно сравнивает третий проход с самым первым и возвращает `False`. Чтобы исправить ошибку, нужно убрать условие `if x not in first:` и всегда обновлять `first[x] = i` (как в решении C).**

Второе ошибочное решение **F**: **В строке `if i >= k + 1:` кандидат удаляет вышедший из окна элемент на шаг позже, чем нужно — в окне одновременно хранится `k + 1` предыдущих элементов вместо `k` (например, на `[1, 2, 1], k = 1` при `i = 2` число `1` с нулевой позиции ещё не удалено из `window`). Чтобы исправить, нужно проверять `if i >= k:` и удалять элемент `nums[i - k]`.**

Как вы искали ошибки: чтением кода, стресс-тестом или и так и так: **Чтением кода и ручной трассировкой на коротких краевых примерах (повторы на расстоянии `k + 1` и серия из трёх одинаковых пропусков).**

Одно из ошибочных решений проходит все три примера из условия. Какое,
и какого примера в условии не хватает, чтобы его поймать: **Все три примера из условия (`[7, 3, 7]` при `k = 2` и `k = 1`, `[5, 5]` при `k = 0`) проходит решение E, потому что в этих тестах каждый номер пропуска встречается максимум дважды. Чтобы его поймать, не хватает примера с тремя одинаковыми элементами, где первые два далеко друг от друга, а второй и третий — рядом (например, `[1, 2, 1, 1], k = 1`).**

## 3. Гонка


Совпала ли гонка с вашей таблицей: у каких решений время растёт вместе с k: **Да, полностью совпала: время растёт вместе с увеличением `k` только у решений A и B (сложность O(n·k)), а у решений C, D, E и F (сложность O(n)) время остаётся практически постоянным при любом `k`.**

A и B — оба O(n·k), но B заметно быстрее. Почему, если сложность одинаковая: **В решении A вложенный цикл и поэлементное сравнение `nums[i] == nums[j]` выполняются на уровне медленного байт-кода Python, тогда как в решении B взятие среза и оператор `in` реализованы внутри интерпретатора на оптимизированном языке C.**

## 4. Решение интервьюера

C и D работают за O(n). Какое из них вы бы взяли и в каком случае
выбрали бы другое: **Для реального кода я бы взял решение C (словарь `last`), так как оно проще и понятнее читается без ручного слежения за границами удаления из окна. Решение D (множество `window`) стоит выбрать, если поток событий `nums` очень длинный (миллионы разных пропусков), а окно `k` небольшое — тогда D займёт всего O(k) памяти вместо O(n) у словаря всех уникальных пропусков.**
