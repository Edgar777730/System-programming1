## 1. Redis: вытеснение ключей при нехватке памяти

Redis — база данных «ключ → значение», которая держит все данные в памяти.
Её часто ставят кэшем перед медленной базой, как в модуле 20. Что делать,
когда память дошла до предела `maxmemory`, задаёт политика вытеснения.
Например, `allkeys-lru` удаляет ключи, к которым давно не обращались.

### 1.1. Приблизительный LRU

Как Redis выбирает ключ для вытеснения: **Redis не перебирает все ключи в базе, а берёт небольшую случайную выборку ключей (по умолчанию `maxmemory-samples` = 5 штук), проверяет у каждого метку времени последнего обращения и удаляет самый старый из этой выборки.**

В модуле 20 точный LRU хранил словарь и двусвязный список: у каждого узла
два указателя по 8 байт. При 10 000 000 ключей это 10 000 000 × 2 × 8 =
160 000 000 байт, около 160 МБ только на указатели.

Почему приблизительному LRU этот список не нужен и чем Redis за это платит: **Двусвязный список не нужен, потому что не требуется поддерживать строгий порядок всех элементов при каждом обращении — достаточно хранить в заголовке каждого объекта 24-битную метку времени. Плата за экономию памяти — вытесняется не самый старый ключ во всей базе, а самый старый из случайной выборки.**

### 1.2. LFU

С версии 4.0 в Redis есть LFU: вытесняется ключ, к которому обращались реже всех.
Придумайте последовательность запросов, где LFU оставит в кэше более нужный
ключ, чем LRU: **Кэш вмещает 2 ключа. Сначала 100 раз запрашивают популярный ключ `A`, затем один раз `B`, а потом один раз новый ключ `C`. LRU удалит `A` (так как к нему обращались раньше, чем к `B`), а LFU сохранит часто используемый `A` и вытеснит редкий `B`.**

## 2. Словарь Python и порядок ключей

С Python 3.7 язык гарантирует, что словарь хранит ключи в порядке вставки.
Как это устроено, объясняет письмо 2012 года.

Как устроен словарь по предложению из письма: что хранит массив `indices`
и что хранит массив `entries`: **Массив `entries` представляет собой плотный список записей вида `[hash, key, value]`, который заполняется последовательно. Разреженный массив `indices` играет роль самой хеш-таблицы и хранит только целые числа — индексы, указывающие на позиции элементов в массиве `entries`.**

Почему от такого устройства порядок вставки получается сам собой: **Новые пары «ключ → значение» всегда дописываются строго в конец плотного массива `entries`, поэтому при обычном переборе словаря Python просто проходит по `entries` подряд с начала до конца, автоматически выдавая ключи в порядке их добавления.**

## 3. Git: хранилище «ключ → значение»

### 3.1. Имя объекта

Из чего Git считает SHA-1 для blob-объекта: **Git склеивает ASCII-заголовок вида `blob <размер в байтах>\0` (тип объекта, пробел, длина содержимого и нулевой байт) с сырыми байтами самого файла и вычисляет от этой последовательности 40-символьный хеш SHA-1.**

Код `blob_hash` (вставьте свою функцию):

```python
def blob_hash(data: bytes) -> str:
    header = f"blob {len(data)}\0".encode("utf-8")
    return hashlib.sha1(header + data).hexdigest()
```


### 3.2. Почему это хеш-таблица

В двух папках лежат два файла с одинаковым содержимым. Сколько blob-объектов
для них создаст Git, и на какую структуру из модуля 19 это похоже: **Git создаст только один blob-объект, так как имя объекта зависит исключительно от его содержимого (одинаковые байты дают одинаковый хеш). Это похоже на множество (`set`) или таблицу дедупликации по хешу, где одинаковые значения не дублируются.**

Посчитайте своей функцией хеши `b"hello\n"` и `b"Hello\n"`. Содержимое
отличается одной буквой. Сколько символов хеша совпало на тех же местах
и что это свойство даёт Git: **Для `b"hello\n"` получается `ce013625030ba8dba906f756967f9e9ca394464a`, для `b"Hello\n"` — `e965047ad7c57865823c7d992b1d046ea66edf78`; на одинаковых местах совпало только 2 символа (на позициях 13 и 16). Это свойство (лавинный эффект) гарантирует, что даже малейшее изменение в файле полностью меняет его хеш, исключая случайные коллизии и позволяя мгновенно обнаруживать любые правки или повреждения данных.**
